Осознанные долги с плановым milestone-закрытием. Формат: ID / что / почему сейчас ок / когда закрыть.

## TD-001 — /health: db как tcp-check — ✅ ЗАКРЫТ (M2)
- **Что было:** проверка БД — TCP-коннект, без реального запроса.
- **Закрыто (M2):** `SELECT 1` через Prisma (`$queryRaw`) в apps/api и apps/bot.
- **Ограничение среды:** в песочнице разработки prisma-движки недоступны
  (binaries.prisma.sh вне сетевого allowlist) — живой прогон health с Prisma
  выполняется на машине владельца/CI; логика идентична проверенной через pg.

## TD-002 — дублирование buildServer/health в apps/api и apps/bot

- **Почему ок:** Э5 фиксирует scope `packages/shared` как «zod-схемы, типы, таксономия» — серверный билдер туда не кладём; дублирование ~50 строк до первой расходимости.
- **Когда закрыть:** при первом реальном расхождении bot/api (M5+), вынести в `packages/*` по согласованию с владельцем.

## TD-004 — compose-файлы не прогнаны локально в песочнице разработки
- **Что:** среда разработки без docker; валидация `docker compose config -q` выполняется в CI.
- **Почему ок:** GitHub-раннер с docker выполняет шаг в каждом пайплайне; YAML дополнительно проверен парсером.
- **Когда закрыть:** первая выкладка на VPS (M10) — `docker compose -f infra/compose.base.yml up -d` на реальном хосте.

## TD-006 — CI: шаг `prisma migrate diff` (урок M2: segments_code_key)
- **Что:** schema.prisma ↔ миграции могут разойтись; «живые проверки инвариантов» этого не ловят.
- **Когда закрыть:** как только ci.yml попадёт в ветку (нужно право workflows) — добавить шаг
  `pnpm --filter @tas/db exec prisma migrate diff --from-schema-datamodel prisma/schema.prisma --to-migrations prisma/migrations --script` (пустой вывод = ок).
- **Статус:** ждёт доступа (см. M1-блокер workflows).

## TD-005 — среда разработки: prisma-движки недоступны (binaries.prisma.sh вне allowlist)
- **Что:** в песочнице нельзя выполнить `prisma generate/migrate` (движки качаются с binaries.prisma.sh).
  Локально установлены type/runtime-заглушки `@prisma/client/.prisma/client` (только node_modules,
  не в git); миграция `0_init` применена к локальной БД через чистый `pg`-драйвер и верифицирована.
- **Почему ок:** на машине владельца и в GitHub CI сеть полная — `pnpm install` (postinstall generate),
  `migrate deploy`, seed работают штатно. CI остаётся авторитетным гейтом.
- **Когда закрыть:** опционально — CI-workflow, выгружающий сгенерированный клиент artifact'ом
  (потребует права workflows на платформе); либо работа в среде с полным доступом.
- **M3-дополнение:** заглушка живёт в `node_modules/.pnpm/@prisma+client@*/node_modules/.prisma/client/`
  (именно туда резолвится bare-спецификатор `.prisma/client/default`); ЛЮБОЙ `pnpm install` затирает её —
  пересоздавать (скрипт-инструкция в AN-17/runbooks M10). Установка в песочнице: `pnpm install --ignore-scripts`.

## TD-007 — собственный HS256 JWT вместо jsonwebtoken
- **Что:** jwt.ts (~60 строк): HS256, обязательный exp, timingSafeEqual, отказ от alg≠HS256.
- **Почему ок:** меньше зависимостей (правило M4), поверхность мала, покрыта тестами (roundtrip/tamper/exp/alg-none).
- **Когда закрыть:** по желанию владельца — заменить на `jsonwebtoken` без смены сигнатур (AN-18).

## TD-008 — idempotency: параллельные запросы с одним ключом (владелец, после M4)
- **Что:** `idempotency.ts` гарантирует единственный **обработчик** только при
  последовательных повтораx (SET NX → проигравший читает результат победителя).
  При ПАРАЛЛЕЛЬНЫХ запросах с одним ключом возможен гоночный двойной запуск
  обработчика до фиксации результата (повтор получит корректный ответ, но
  side-effect мог выполниться дважды).
- **План:** reserve-паттерн (двухфаза: reserve → execute → publish) в M6+ при
  появлении дорогих mutations; текущий кейс (issue tracking-link) дублирует
  только вставку-ссылку, риск низкий.
- **Статус:** принято владельцем как ограничение M4 (2026-08-29).

## TD-007 (дополнение владельца, после M4) — verifyJwt не валидирует role против enum
- **Что:** `verifyJwt` проверяет `role` только как `typeof string`; значение не
  сверяется с `('owner'|'editor'|'viewer')`.
- **Фактический риск:** низкий — токен подписывается нашим `signJwt` после login
  (role из enum БД), а вес неизвестной роли = `undefined` → NaN-сравнения в RBAC
  дают 403 на всех защищённых роутах. Прямой exploit требует секрета JWT.
- **План:** добавить zod-проверку role в verifyJwt (+ тест на role:'admin') при
  первом касании auth-кода (M6+ / hardening-проход).
- **Статус:** ЗАКРЫТО в M6 (2026-08-29): verifyJwt валидирует role по enum
  ADMIN_ROLES = ['owner','editor','viewer']; тест на подданную роль 'admin'
  (`apps/api/test/jwt.test.ts`) — 401.

## TD-009 (опционально, владелец) — dummy-argon2-verify при неизвестном email
- **Что:** при неизвестном email login отвечает 401 сразу после SELECT, не делая
  argon2-verify → тайминг-оракул существования email (ответ при неизвестном email
  быстрее). Перечисление смягчено lockout 5×15мин/email, но не устранено.
- **План:** при неизвестном email выполнять verify против фиксированного
  dummy-хэша (константа в коде) — тайминг выравнивается. Реализация ~5 строк +
  тест, по решению владельца.

## TD-010 — лид-магнит из приватного S3 (решение владельца)
- **Что:** сейчас файл доставляется по публичному HTTPS-URL (`sendDocument(url)`,
  AN-23) — Telegram скачивает его сам. Приватный бакет потребует скачивания
  ботом + multipart-загрузки в Telegram.
- **Нужно:** пакет `@aws-sdk/client-s3` (вне §20) ИЛИ presigned-URL'ы. Запрос
  одобрения владельца; при одобрении — реализация в M6+ без смены контракта
  (delivery_kind: 'file' | 'link' уже в схеме события).

## TD-011 — два Bot API-клиента: grammY (bot) и fetch-транспорт (worker)
- **Что:** после миграции отправителя в worker (AN-25) в репозитории два
  независимых клиента Bot API: grammY-инстанс в `apps/bot` (только inbound
  webhook + эфемерный ack) и fetch-транспорт `apps/worker/src/telegram.ts`
  (все исходящие). 429/timeout-семантика дублируется в двух местах.
- **Почему оставлено:** worker намеренно без grammY-стека (никаких
  middleware/сессий — только sendMessage по HTTP из senderCore); боту grammY
  нужна для webhook-конвейера. Свести к одному клиенту = тащить grammY в
  worker или писать свой webhook-слой — оба варианта дороже дублирования.
- **План:** пересмотреть при M10 (deploy/hardening): вынести transport в
  `packages/shared` либо перейти на grammY в worker, если появится
  потребность в других методах Bot API.
- **Статус:** принято в рамках M6 (2026-08-29).
